# WordPress bridge validation

Run from the repository root:

```bash
python3 -B tests/wordpress/static_checks.py
python3 -B tests/wordpress/run.py
```

The first command performs **source-only** checks. It does not parse or execute PHP, load WordPress or validate a live website.

The second command requires a real `php` executable, version 7.4 or later. It fails with an actionable error when PHP is unavailable. With PHP available, it lints all bridge/test PHP files, runs the real bridge code against small WordPress API doubles, and validates JSON from the builder and successful admin download path. It requires no database, credentials, network connection or third-party packages.

The PHP contracts cover permission denial, route registration, nonce and method rejection, public-post filtering, password/private-content exclusion, raw metadata semantics, pagination, UTF-8 bounds, NUL/unexpected metadata handling, timestamps, no-store response headers, native admin links and whole-export size limits. The doubles intentionally fail if selected mutation/outbound functions are called.

`fixtures/snapshot.json` is **synthetic contract data**, not an observation from WordPress or proof that a provider integration worked. To inspect output generated by the PHP bridge itself against the doubles:

```bash
php tests/wordpress/contract.php --snapshot
php tests/wordpress/contract.php --download
```

Neither command boots WordPress. Real cookie/Application Password authentication, REST routing, HTTP headers, plugin lifecycle, database behaviour, third-party hooks and actual Yoast/Rank Math versions require a separate authorised WordPress staging check. No such integration run is claimed by these tests.

The local implementation environment did not provide PHP. The source-only checks can run there; PHP lint and contract execution remain unverified until this runner succeeds in an environment or CI job with PHP installed.
